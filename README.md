# rpi_photonics_sim

A handheld optics simulator. A Raspberry Pi, a 2.8 inch SPI TFT, and two
joysticks. You push a beam around a rough mirror with your left thumb and watch
the interference pattern change at 30 frames a second.

I built it as a birthday present for a friend who studies this for a living.

## The device

`mirror_sim_pi.py` is what runs on the hardware. Left joystick moves the beam and
its click cycles six views. Right joystick drives a menu down the right-hand 80
pixels, up and down to pick a parameter and left and right to change it. Holding
the left button for three seconds resets everything.

The six views are mirror roughness, total mirror surface, the interference
pattern, reflected beam phase, beam amplitude, and the correlation matrix.

Eight parameters are live on the menu. Distance from the beam waist to the
mirror, mirror radius of curvature, RMS surface roughness in fractions of a
wavelength, roughness correlation length, which surface model is active, which
correlation matrix is shown, beam markers on or off, and a fidelity setting.

## The physics

A 1 µm Gaussian beam with a 1 mm waist over a 6 mm field of view, reflecting off
a mirror that has both curvature and roughness. All of it is in
`mirror_physics.py`, which is 250 lines and the only file you need to read to
understand what the device computes.

The beam carries full Gaussian optics at the mirror plane, so Rayleigh range,
spot size `w(z)`, wavefront curvature `R(z)` and the Gouy phase. Mirror roughness
is generated by FFT filtering white noise with a Gaussian spectral filter, then
renormalised to a target RMS height `σ_h` selectable in fractions of λ from 0 to
λ/2. The noise seed is fixed at 42, so the surface stays put while the beam moves
across it rather than resampling under you every frame.

Reflection is

```python
E_ref = A * np.exp(-1j * phi_inc) * np.exp(1j * 2 * K * h)
```

The factor of 2 on `K*h` is there because the beam crosses each surface deviation
twice. Interference is `|E_inc + E_ref|²`.

The mirror surface is fixed in the lab frame while the beam translates over it.
`h_quad` uses unshifted coordinates and the beam uses shifted ones, which is why
moving the beam off axis produces off-axis fringes rather than dragging the
pattern along with it.

### The correlation matrix, both ways

`Q_p` is computed two ways and the menu flips between them.

- `statistical` is the ideal analytic form, `exp(-Δr² / ℓ²)`.
- `empirical` samples phase off the mirror surface actually synthesised,
  `(cos(φᵢ - φⱼ) + 1) / 2`.

Watching those two disagree is the point of the toggle. It is also the most
expensive thing the device computes, at O(n⁴), so it runs at 2 Hz and only while
its own view is on screen.

## Prior work

The physics is inspired by

> B. Schreyer, D. Younis, D. Kaganovich, L. A. Johnson, T. M. Antonsen, and
> B. Hafizi, "Realization of nontrivial partial spatial coherence by a
> deformable mirror," *Applied Optics* **64**(17), 2025.
> [doi:10.1364/AO.557755](https://doi.org/10.1364/AO.557755)

That paper generates partially coherent phase screens by singular-value
decomposition of a correlation matrix, realises ensembles of 10,000 screens at
kHz rate on a deformable mirror unit, and measures them with a Shack-Hartmann
wavefront sensor.

This repository contains no part of that paper. Read it at the DOI above.

## What this is not

- It is not a solver. No FDTD, no BPM, no beam propagation of any kind.
- It does not do the SVD ensemble generation the paper runs.
- It does not model a deformable mirror. No actuator grid, no influence
  functions, no stroke limits.
- The physics grid is small because the target was 30 FPS on a Pi 3.

## Run modes

Five entry points. Two are the device, three are development surfaces.

| Entry point | Needs a Pi | What it is |
| :--- | :---: | :--- |
| `mirror_sim_pi.py` | yes | **the device.** SPI TFT, two joysticks over serial |
| `mirror_sim.py` | no | same physics, same six views, pygame and a keyboard |
| `lens_test.py` | no | matplotlib workbench with sliders, where the physics started |
| `tft_emulator.py` | yes | earlier prototype, partial-coherence engine |
| `coherence_emulator.py` | optional | the original, a 32x32 RGB LED matrix |

`web_server.py` serves `device_mockup.html`, a browser build of the prototype
line rather than of the device.

### Without hardware

```bash
python3 -m venv venv && source venv/bin/activate
pip install numpy scipy pygame pyserial
python3 mirror_sim.py
```

WASD moves the beam, arrows drive the menu, Q cycles views, SPACE opens the menu.

### On the device

```bash
sudo python3 mirror_sim_pi.py --driver ili9341 --rotation 90 --serial-port /dev/ttyUSB0
```

`software_setup_guide.md` is the full path from a blank SD card, `build_guide.md`
has the bill of materials, and `wiring_instructions.md` has the breadboard
wiring. Read the known-issues list below before trusting either wiring document.

Four systemd units are included for autostart. They run as root because of SPI
and GPIO access, and a `gpio`/`spi` group user would be better.

## The prototype line

The device started as a 32x32 RGB LED matrix showing a partial-coherence phase
screen, and that lineage is still here. It models something different from the
mirror simulation and shares no code with it.

A phase screen is a field of random optical phase. Uncorrelated point to point is
spatially incoherent light, perfectly correlated is coherent, and the knob that
sets where you are between them is the correlation length. The engine convolves
white phase noise with a kernel, and two kernel families ship, `exp(-r²/ρ²)` and
`1/(1 + (r/ρ)^1.5)`.

Phase is wrapped to (-π, π], so filtering it directly smears the branch cut. The
engine convolves `cos(φ)` and `sin(φ)` separately and recovers phase with
`arctan2`. Same trick in all three ports.

That engine exists three times and each port solves the convolution differently.

| File | Method | Convolution |
| :--- | :--- | :--- |
| `simulation_code.py` | `scipy.signal.fftconvolve` | linear |
| `tft_emulator.py` | cached `np.fft.fft2` multiply | circular, so it wraps at the edges |
| `device_mockup.html` | brute-force spatial loops in JavaScript | linear |

## Making it fast enough

The Pi 3 has to composite a 320x240 frame and push it over SPI 30 times a second.

- Colormaps are precomputed once into 256x3 uint8 lookup tables, so colouring a
  frame is one fancy-index rather than a Python loop.
- The phase colormap is a 3 phase sine wheel that is genuinely cyclic, meaning
  t=0 and t=1 give the same RGB. A wrapped phase display needs that or it shows a
  false seam at ±π.
- Resampling is nearest-neighbour through integer index arrays and `np.ix_`,
  which skips PIL's resize entirely.
- Serial input is read drop-to-latest rather than line by line, so a backlog in
  the buffer never becomes control lag.
- The joystick deadzone is 50 counts out of 1024 and rescales over the remaining
  462, so there is no discontinuity at the deadzone edge.
- Fidelity is one knob moving display resolution and `Q_p` grid size together,
  from 8/4 up to 240/24.

## The debugging log

Six scripts here are not tools. They are a record of one evening spent on an
ILI9341 that initialised without raising and displayed nothing.

| Script | What it was chasing |
| :--- | :--- |
| `hardware_test.py` | does the happy path work at 1 MHz |
| `diagnose.py` | sweep driver against chip-select at 8 MHz |
| `slow_diagnose.py` | is it a clock speed problem |
| `pin_search.py` | sweep pin assignments |
| `soft_spi_test.py` | rule out the hardware SPI driver |
| `touch_debug.py` | XPT2046 resistive touch |

Three things that log records honestly.

Clock speed was never the fault. Those scripts walk down from 8 MHz to 1 MHz and
production ships at 64 MHz.

`pin_search.py` labels `CE0/D24/D25` as "Golden Standard" and `CE1/D24/D25` as
"Old Standard". Production runs CE1, which is what my own wiring guide said all
along.

`soft_spi_test.py` claims in its header to bit-bang SPI and bypass the hardware
driver. It calls `busio.SPI`. It is ordinary hardware SPI, so it never tested
what it says it tests and the driver was never eliminated as a suspect.

Touch was cut. `tft_emulator.py` reads `# Touch Config (XPT2046) - REMOVED` and
the pin it used became a button. The likely reason it never worked is that
`touch_debug.py` creates the interrupt line with no pull-up. PENIRQ is
open-drain, so the line floats and the read is noise.

## Known issues

Fixed before publishing:

- `web_server.py` served arbitrary files. The containment check was a string
  prefix test on an unresolved path, so a request target with no leading slash
  kept its `..` segments and escaped the repository root. It returned `/etc/hosts`
  over HTTP. It now resolves with `realpath` before comparing. The unit file runs
  as root on `0.0.0.0`, which is what made it worth fixing rather than noting.
- `device_mockup.html` had a radix-2 FFT whose butterfly wrote results back into
  its input slots instead of the output slots. Measured against numpy at N=32 it
  was off by 24.7 in absolute magnitude, and it was not a permuted transform
  either. The Beam view was showing a plausible-looking wrong answer. Now exact
  to 4e-15.
- `tft_emulator.py` raised `AttributeError` on any button press off-Pi, because
  the serial branch of `update()` runs before the hardware guard.
- Kernel centring used `-h//2`, which Python parses as `(-h)//2`. The kernel is
  always odd sized, so every convolved frame was translated by one pixel.

Still open:

- **No Arduino sketch is in this repository.** Both Pi entry points need a device
  streaming 7 comma-separated integers at 9600 baud, and the firmware for it is
  not here and is not documented anywhere. This is the largest gap between what
  is published and what is needed to rebuild the device.
- `build_guide.md` disagrees with the built device. Its pinout puts TFT chip
  select on CE0 where the code and `wiring_instructions.md` use CE1, its bill of
  materials says the controller is a web interface, and it references a
  `wiring_diagram.svg` that does not exist.
- `wiring_instructions.md` mislabels two buttons. GPIO 6 is listed as a source
  toggle and is a resolution cycle in code. GPIO 27 is listed as a size cycle and
  is a speed decrement. Its own summary table puts TFT D/C on GPIO 18 while the
  wiring table and both CLI defaults say GPIO 24.
- `pyserial` is hard-imported by both Pi entry points and installed by none of
  the setup guides.
- `--physics` in `tft_emulator.py` is declared and read nowhere. The grid starts
  at 240 and changes only via the GPIO 6 button.
- The MCP3008 path in `tft_emulator.py` constructs its channels and never reads
  them, so `--no-adc` does nothing and a device built to the digital-only wiring
  cannot change ρ at all.
- Torn serial lines parse as valid data. `read_all()` has no line-boundary sync,
  so a truncated fragment that still holds 7 fields yields a bogus joystick value
  with no exception. Any parse failure then closes the port for 2 seconds, so a
  malformed line and a real USB unplug are handled identically.
- `mirror_sim_pi.py` cycles the view on press rather than release, so a
  hold-to-reset fires a view change first, then re-arms and repeats every 3
  seconds while held.
- The beam Y sign in `mirror_sim_pi.py` contradicts the axis remap comment above
  it. One of the two is stale and it needs a bench check.
- `mirror_sim.py` decrements its menu cooldown twice per frame, so the desktop
  menu repeats about twice as fast as the device.
- `_send_file` in `web_server.py` catches only `FileNotFoundError`. A directory
  request raises `IsADirectoryError` and escapes.
- `lens_test.py` carries an older copy of the mirror physics whose
  `compute_Qp_matrix` takes two parameters it never uses and whose `Q_p`
  reference scale is resolution-dependent. `mirror_physics.py` is the maintained
  one.
- `_generate_perlin_noise` in `tft_emulator.py` is a sum of sinusoids and not
  Perlin noise.
- The FFT roughness filter produces a real 1/e autocorrelation length about 2.0
  to 3.0 times the `corr_len` parameter, falling off at large values from field
  of view truncation, while the statistical `Q_p` uses the bare parameter. The
  two panels do not use the same definition of ρ₀.
